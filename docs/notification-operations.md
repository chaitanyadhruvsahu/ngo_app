# Automatic job updates and announcements

Job reminders now run automatically through the existing delivery command. Active assignments receive an assignment update, then reminders one day before their deadline, on the due date, and once when overdue. Each stage is unique per job, assignment revision and deadline, so retries do not send duplicates. Jobs without deadlines receive the assignment update only. Submitted and approved jobs stop receiving deadline reminders. Pending updates for changed assignments or deadlines are cancelled before delivery.

Deadline dates use `JOB_REMINDER_TIME_ZONE`, defaulting to `Asia/Kolkata`; stored timestamps remain UTC. Reminders become eligible at the start of the relevant date in that timezone and are delivered on the next worker run. The worker does not backfill missed historical stages.

Staff use **Send announcement** for bilingual team news, training and events, targeting a person or block. Announcements send immediately by default or at the selected schedule. The interface no longer asks staff to create job reminders. The Updates inbox includes automatic job links and announcements, with category filters, read state, manual refresh and a 30-second refresh while open. Only in-app delivery is implemented.

The deployment operator must run `python manage.py deliver_notifications` every minute from the backend directory with the same environment and database credentials as the web application. Use the host's existing cron or systemd timer. The command is deliberately short-lived; there is no task queue. This repository does not install a host timer or alter the user's crontab. Capture command exit codes and stderr in the host's normal operational logs. An exception produces a nonzero exit; the next invocation retries unfinished work.

Due means `scheduled_time - remind_before <= command_start_time`. A notification locks its database row, creates one recipient row per eligible active user, then records `delivered_at` in the same transaction. PostgreSQL row locks serialize overlapping workers; a unique recipient constraint prevents duplicate recipients. Failure rolls back that notification's work. Earlier notifications completed in the same run remain completed and are skipped on retry. A successful delivery with no eligible recipients is final.

For block targets, active fellow membership is resolved at delivery time. Already-delivered history remains with the recipient if they later change blocks. Disable accounts through the existing account mechanism; disabled users cannot sign in. Messages cannot be edited or deleted through the notification API after creation, preventing silent changes to recipient history. Read and dismiss operations are idempotent and scoped to the authenticated recipient. Dismissing also marks read.

Verification on 2026-09-24: eight backend tests passed against local PostgreSQL, including simultaneous worker delivery; SQLite passed seven and explicitly skipped the PostgreSQL lock test. Tests also cover the exact microsecond due boundary, membership snapshot, transaction rollback/retry, recipient privacy and authorization, and bilingual creation validation.
